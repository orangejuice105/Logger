# 性能基线

在项目根目录运行：

```bash
python3 benchmarks/run_benchmark.py
```

保存环境、逐轮结果和中位数：

```bash
python3 benchmarks/run_benchmark.py --output /tmp/logger-benchmark.json
```

默认每种配置预热一次，然后正式测量三次，每次提交 100000 条、每条正文
128 个 ASCII 字节。需要 g++ 和 Python 3，脚本使用标准库，无第三方依赖。
临时日志和可执行程序会自动清理，仅显式指定的 JSON 报告会保留。

参数可调整：

```bash
python3 benchmarks/run_benchmark.py --messages 20000 --message-bytes 128 --repeats 3
```

## 测量定义

| 指标 | 计时或统计方法 |
|---|---|
| `mean_call_us` | 每次 `log()` 前后读取 `steady_clock`，所有生产线程的调用耗时总和除以提交条数 |
| `submit_ms` | 生产线程全部准备好后统一放行，到所有生产线程 join 完成的实际经过时间 |
| `full_ms` | Python 从启动 C++ 子进程前，到该进程完全退出后的实际经过时间 |
| `attempts_per_second` | 总提交条数除以提交阶段时间，包含被队列丢弃的尝试 |
| `written_per_second` | 实际写入条数除以完整处理时间 |
| `dropped` | 因共享队列满而丢弃的新日志条数 |
| `queue_peak` | 共享队列历史峰值，不包含后台线程的局部批次 |

完整处理时间包含进程启动、Logger 初始化、生产线程创建、提交、后台排空和
文件关闭；不包含编译、文件内容核对和清理。当前 API 没有显式 shutdown，
所以利用进程退出等待单例析构，避免把尚未完成消费的时间当成完整写入时间。

正文在计时前构造，所有消息以 INFO 提交，最低级别为 INFO。计时包含 Logger
内部时间格式化、消息复制、队列锁竞争等调用工作。逐条计时本身也有开销；
多线程的耗时总和不能当成实际经过时间，因此单独记录提交阶段时间。

## 对比配置

| 配置名 | 生产线程数 | 批次上限 | 共享队列容量 |
|---|---:|---:|---:|
| `single_batch1` | 1 | 1 | 总提交条数 |
| `single_batch100` | 1 | 100 | 总提交条数 |
| `four_batch1` | 4 | 1 | 总提交条数 |
| `four_batch100` | 4 | 100 | 总提交条数 |
| `four_default_queue` | 4 | 100 | 10000 |

前四项容量足够容纳本轮全部提交，便于比较不丢日志的情况。第五项使用 Logger
默认容量，观察有限队列下的丢弃情况。批次大小是上限，后台线程不会为了凑满
一批而等待，因此实际每批不保证达到 100 条。

滚动阈值设置为 `uintmax_t` 最大值，避免滚动和归档淘汰影响本基线。脚本在
进程退出后流式读取文件，检查每条日志正文和换行完整，并要求：

```text
实际写入条数 + 队列丢弃条数 = 总提交条数
```

出现文件错误或非预期归档时，整次基线失败，不报告有效吞吐量。不能将丢弃
大量日志时的提交速度，作为完整写入能力。

## 结果的适用范围

结果受 CPU、系统负载、编译参数、文件系统和缓存状态影响。报告保存这些环境
信息和源码 SHA-256；对比时应使用相同消息长度、配置、编译参数和文件系统。
预热在独立进程中进行，不构成长期服务器稳态测试。默认报告三轮中位数，
原始每轮结果保留在 JSON 中，方便观察波动。

`flush()` 和文件关闭不等于 `fsync()`；这里测量数据交给文件系统后的完成时间，
不测量断电持久化。结果也不证明 HTTP Server 的性能。
