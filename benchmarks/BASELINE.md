# 初始性能基线

测量时间：2026-10-12 13:52（Asia/Shanghai）。完整 UTC 时间戳、源码 SHA-256、
预热及每轮原始数据保存在 [baseline.json](baseline.json)。

复现命令，在项目根目录运行：

```bash
python3 benchmarks/run_benchmark.py --output /tmp/logger-benchmark.json
```

## 环境与负载

- 系统：WSL2 Linux 6.6.114.1，x86_64，glibc 2.35。
- CPU：AMD Ryzen 9 7940HX；环境可见 32 个逻辑 CPU。
- 内存：WSL 环境可见约 7.36 GiB，不代表物理主机的全部内存。
- 输出位置：系统临时目录，文件系统为 ext4。
- 编译器：Ubuntu g++ 11.4.0；Python 3.10.12。
- 编译参数：`-std=c++17 -O2 -DNDEBUG -Wall -Wextra -Wpedantic -pthread`。
- 每轮提交 100000 条 INFO 消息，最低级别 INFO；每条正文 128 个 ASCII 字节。
- 每种配置独立预热 10000 条，正式测量 3 轮；每轮使用新文件。
- 滚动阈值设为极大值，避免归档淘汰影响核心异步写入计数。

## 如何理解

本次工作负载下，批次上限为 100 的完整处理时间明显低于批次 1，并且共享
队列积压更小。这与减少批次分配、锁交接和文件刷新频率的方向一致；具体
贡献没有通过性能分析工具分离，不能把所有改善都归因于单一操作。

四个生产线程在本次测量中没有带来更高的完整写入吞吐。逐次调用时间也包含
并发等待和调度影响；具体瓶颈需要进一步分析。默认容量与大容量在批次 100
下都没有溢出，小幅差异不构成队列容量影响性能的普遍结论。

调用返回只代表提交阶段结束。批次 1 场景的提交时间与完整时间相差较大，
说明后台尚有日志需要消费，不能用提交条数除以提交时间代替完整写入吞吐。

这是一份短时间、本机、文件缓存参与的初始基线。未固定 CPU 频率和调度，
未逐一注入磁盘错误，也没有使用 fsync 测量断电持久化。完整测量定义与限制
见 [README.md](README.md)。后续修改应在相同环境和参数下重新比较逐轮数据。
